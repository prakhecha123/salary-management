# Deployment (Render)

`render.yaml` at the repo root is a
[Render Blueprint](https://render.com/docs/blueprint-spec) defining three
resources: the Rails API, a Postgres database, and the React app as a static
site.

## First deploy

1. Push this repo to GitHub.
2. In the Render dashboard: **New > Blueprint**, point it at the repo. Render
   reads `render.yaml` and provisions all three resources together.
3. Wait for the API and frontend builds to finish.
4. Seed the database once, from the Render dashboard's Shell tab on the
   `salary-management-api` service:
   ```
   bundle exec rails db:seed
   ```

Seeding is **not** wired into `buildCommand`. `db:seed` deletes and
regenerates all data (see `backend/db/seeds.rb`), so running it on every
deploy would silently wipe out anything entered through the app between
deploys — a fine trade-off for a demo/take-home, but not a habit worth
normalizing in the deploy config itself. Run it once after the first deploy;
re-run manually only if you want to reset back to fresh seed data.

## Notes

- The two service URLs in `render.yaml` (`FRONTEND_ORIGIN`, `VITE_API_URL`)
  assume the default service names below. If Render assigns different
  subdomains, update both env vars to match before (or after) the first
  deploy and redeploy.
- Render's free web service tier spins down after 15 minutes of inactivity;
  the first request after idling takes ~30–60s to wake up. Fine for this
  assessment, worth mentioning if giving a live demo cold.
- `SECRET_KEY_BASE` is generated by Render (`generateValue: true`) rather
  than relying on `config/master.key`, since that file is gitignored and
  never committed.
