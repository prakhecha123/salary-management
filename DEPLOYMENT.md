# Deployment (Render)

`render.yaml` at the repo root is a
[Render Blueprint](https://render.com/docs/blueprint-spec) defining three
resources: the Rails API, a Postgres database, and the React app as a static
site.

## First deploy

1. Push this repo to GitHub.
2. In the Render dashboard: find **Blueprints** in the left sidebar (it's a
   separate section from the generic "New +" resource picker, which only
   offers single resources) → **New Blueprint Instance** → point it at the
   repo. Render reads `render.yaml` and provisions all three resources
   together.
3. Wait for the API and frontend builds to finish.
4. **Check the actual assigned URLs.** Render only gives you the exact
   `salary-management-api.onrender.com` / `salary-management-frontend.onrender.com`
   names if they're not already taken by another Render user — otherwise you
   get a random suffix (e.g. `salary-management-api-k4bb.onrender.com`). Open
   each service's page and note its real URL, then update both cross-
   referencing env vars to match:
   - `salary-management-api` → Environment → `FRONTEND_ORIGIN` = the
     frontend's real URL
   - `salary-management-frontend` → Environment → `VITE_API_URL` = the
     backend's real URL (this one matters more: Vite bakes it into the JS
     bundle at build time, so just saving the env var isn't enough — trigger
     **Manual Deploy → Deploy latest commit** on the frontend afterward)
5. Seed the database once. **On Render's free plan, the Shell tab requires
   the paid Starter plan** ("Shell is not supported for free compute
   plans") — there's no need to pay for this. Instead, connect directly from
   your own machine using the database's **External Database URL** (find it
   on the `salary-management-db` page, under Connections):
   ```bash
   cd backend
   RAILS_ENV=production DATABASE_URL="<external database url>" bundle exec rails db:seed
   ```
   Treat that connection string as a real production credential — rotate it
   afterward if it's touched anywhere outside Render's own dashboard.

Seeding is **not** wired into `buildCommand`. `db:seed` deletes and
regenerates all data (see `backend/db/seeds.rb`), so running it on every
deploy would silently wipe out anything entered through the app between
deploys — a fine trade-off for a demo/take-home, but not a habit worth
normalizing in the deploy config itself. Run it once after the first deploy;
re-run manually (same command) only if you want to reset back to fresh seed
data.

## Gotchas actually hit deploying this

- **`type: static` doesn't exist.** Render's current Blueprint schema wants
  a static site declared as `type: web` with `runtime: static`, not
  `type: static` — the older convention. Render's Blueprint parser rejects
  the file outright with "unknown type" if you get this wrong, before
  creating anything.
- **A query that passes every test can still fail on the real production
  database.** `PayrollAnalytics`'s median query worked in all 51 RSpec
  examples (SQLite) and then threw `PG::GroupingError` on first real
  request in production (Postgres): SQLite silently allows selecting a bare
  non-aggregated column alongside an aggregate with no `GROUP BY`; Postgres
  correctly rejects it per the SQL standard. The fastest way to actually
  diagnose this kind of thing, rather than guessing from an opaque 500 with
  an empty body: run the failing code directly against the production
  database from a local `rails runner`, using the External Database URL —
  same one-liner as the seeding step above, but calling the code path that's
  failing instead of `db:seed`. Full local Rails error output, against the
  real database, in seconds — much faster than reading Render's log viewer.
- **Render's free web service tier spins down after 15 minutes of
  inactivity**; the first request after idling takes ~30–60s to wake up.
  Fine for this assessment, worth mentioning if giving a live demo cold.
- `SECRET_KEY_BASE` is generated by Render (`generateValue: true`) rather
  than relying on `config/master.key`, since that file is gitignored and
  never committed.
